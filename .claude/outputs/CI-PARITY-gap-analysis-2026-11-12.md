# OW CI/CD gap analysis against OSE (2026-11-12)

Subject: ourWKRP `origin/main` at `aec9dbf` compared with ourSharedEvents `main` at `39985a98`.
Status: **draft for the owner. Nothing is built until the owner agrees the plan in section 5.**

## 1. Three findings that come before any new gate

1. **The staging deploy has not passed since June.** Every push to `main` since at least 2026-10-01 ends red. The last green `CI` run on `main` was on 2026-06-09.
   - Every gate passes, and so do migrations and `wrangler deploy`. Then `Smoke — prove controls are live (staging)` fails: it cannot open a TLS connection to `stg.ourwkrp.com` (`SSL alert number 40`, run 41414964022, 2026-11-02).
   - A curl from this workstation fails the same way, while `stg.oursharedevents.com/health` returns 200.
   - This is an edge setting (the custom domain or certificate for `stg.ourwkrp.com`), so it is the owner's to fix. Until it is fixed, no staging tier of any kind can be green on OW, and an OSE-style "Done" bar cannot be met.
2. **Only two checks are required on `main`:** `S0 Security` and `Validate against OCR-docs brain`, as read from the branch protection API.
   - Unit, integration, contract, security, E2E, Bruno, fuzz and performance are all advisory, so a PR can merge with a red test.
   - `All Checks Passed` exists but is not required.
3. **`All Checks Passed` cannot report a failure.** It uses plain `needs:` with no `if: always()`. When any test job fails, the aggregate is skipped, not failed (ci.yml L387-404), and a skipped required check counts as passing in GitHub.
   - OSE's aggregators use `if: always()` and an explicit result check (`gate-tests`, `contract-staging`, and the others).

## 3. What OW does better (OSE should consider adopting)

1. **A fuzz/property layer as its own gate on every PR.** `tests/fuzz/` has 4 files and 17 properties with fast-check, covering every untrusted-input boundary OW has: CSV import parser, pagination cursors (including the unicode `btoa` regression), catalog query sanitisers (FTS operators, `LIKE` escaping, numeric clamps) and route-path/UUID extraction. It runs as `Fuzz / Property Tests` on every PR.
   - OSE has fast-check in only two specs: `tests/fat-finger.property.spec.ts` and `tests/red-team/auth-jwt-fuzz.property.spec.ts`. Its overnight deep run covers only the first.
   - OSE candidates: the `/api/v2/events/map` coordinate refusal, H3 cell parsing, `count-floor.ts` (`floorTotalOfParts` never reveals a part below 5), `public-event-projection.ts` (the output never carries a key outside the allowlist), language tag parsing and the `/q` / `/s` token decoders.
2. **Proof at deploy time that controls are live.** OW's deploy job asserts that controls fire on the deployed Worker (`scripts/smoke.mjs`): a recognised rate-limiter backend, a nonce CSP on HTML, `script-src 'none'` on JSON, a cross-origin mutation refused with 403, and 429 under burst.
   - OSE's T1 checks only `/health` and leaves security behaviour to T3. A control that is wired but dormant (for example a rate-limit binding that falls back to "allow") passes OSE's T1.
3. **A wiring preflight before deploy**, the same check locally and in CI (`npm run preflight:staging`, `predeploy:*` hooks). OSE has pieces of this (`check-binding-placeholders.mjs`) but no single "refuse to deploy without security wiring" step that a developer also runs locally.
4. **Scanners as pure functions with a broken fixture on every PR** (`tests/support/determinism-scan.ts`). The failure path is exercised in CI every time, not once by hand. OSE has the same idea in its `--self-test` scripts, but not for its 37 structural `0-architecture` invariant specs, which run raw Playwright with no zero-test guard.
5. **Born-red mutants inside the showcase workflow** (ourWKRP#106, not merged yet). It plants faults in a copy of the library and requires every check to fail on every run. That is born red executed by CI, not just recorded. OSE records born red as annotations (conformance report) and as script self-tests.

**Noticed in OSE while comparing** (for the OSE side; not acted on here):
- `mutation` and `mutation-ci-scripts` are not in `tools/ci/main-branch-protection.json`, although the workflow says the owner wants them required.
- The per-file mutation floors are "never lower" by convention only. No base-branch comparison exists, unlike `.ocr-design-check.json`.
- These steps have no zero-test check: T0 invariants, the T0 vitest sections, staging T2 Bruno, staging T3, T4c / T4c-phase2 and the production smoke.
